## 2. Important findings

- **The loop does not verify that a final answer is evidence-backed, and this gap is untested, not just documented.** `run_agent` (`src/operations_agent/agent.py:80-103`) returns `StopReason.COMPLETED` whenever `turn.final_text is not None`, with no check against prior `ToolResult.status` values. The work log (`reports/ai-work-log.md:57,70-72,244-247,260-267`), state diagram (`reports/state-diagram.md:100-104`), final report (`reports/final-report.md:146-167`), and broken-loop review (`reports/broken-loop-review.md:127-139`) all disclose this repeatedly and honestly — but disclosure is not the same as a test. There is no scripted scenario or unit test that feeds the loop a `final_text` immediately after a `NOT_FOUND`/`RETRYABLE_ERROR`/`TERMINAL_ERROR` result to confirm the trace *would* make the mismatch detectable (vs. just asserting the code doesn't crash). S03 and S05 happen to use scripted models that behave well; nothing forces or exercises the adversarial case the comprehension gate warns about. This is the single biggest residual risk against "Can unsupported answers after not-found or terminal errors be detected?" — detectable in principle (trace has `call_id`-correlated statuses), but never actually demonstrated by an automated check.

- **`TOTAL_CALL_LIMIT` and `EMPTY_TURN`/`MODEL_ERROR` stop reasons are implemented but have zero test or scenario coverage.** `agent.py:120-121` enforces `max_total_tool_calls`, and `agent.py:68-69,105-106` enforce `MODEL_ERROR`/`EMPTY_TURN`, but `grep` across `tests/*.py` and `fixtures/scenarios.json` shows no scenario or unit test ever drives these three paths (only `ITERATION_LIMIT` and `REPEATED_CALL_LIMIT` are exercised, via S07/S08). PROJECT.md's required-path list ("sequential, parallel, invalid-args-then-correction, retryable-then-retry, terminal error, not found, repeated-call limit, iteration limit") does not name total-call-limit, empty-turn, or model-error explicitly, so this isn't a spec violation, but it is an untested code path that the final report concedes only in passing (`reports/final-report.md:76-78`: "not exercised by the default scenario set"). `ai-work-log.md:155-159` separately flags that only `ModelGatewayError` is caught, and other exception types from a live session could propagate uncaught — this remains true and unverified.

- **Live `ClaudeSession` is not covered by any automated test**, by design per PROJECT.md ("Live calls are excluded from default tests," PROJECT.md:97) — but note `tests/test_model.py` only tests `ScriptedModelSession`, so a regression in `ClaudeSession`'s tool-schema conversion, message-list bookkeeping, or `APIError`→`ModelGatewayError` mapping would not be caught by CI. This is disclosed in `reports/ai-work-log.md:216-219` and `reports/final-report.md:174-176`.

- **Environment-variable documentation is inconsistent with the actual Bedrock auth path.** `.env.example` lists `ANTHROPIC_API_KEY=` and `ANTHROPIC_MODEL=`, and `cli.py:75` reads `os.environ["ANTHROPIC_MODEL"]`, but `ai-work-log.md:180-183` states `AnthropicBedrock` actually authenticates via `AWS_BEARER_TOKEN_BEDROCK`/`AWS_REGION`, not `ANTHROPIC_API_KEY`. `ANTHROPIC_API_KEY` in `.env.example` appears to be a leftover/unused variable for this adapter — minor, but worth a one-line correction so a learner or mentor doesn't set the wrong credential expecting it to work.

- **Disclosed provider deviation (Claude/Bedrock instead of OpenAI/Responses) is real and consistently documented**, not just claimed. `src/operations_agent/model.py:71-136` implements `ClaudeSession` against `AnthropicBedrock`, converts tool schemas at `model.py:60-68`, and `pyproject.toml`'s `dependencies = ["anthropic", "pydantic"]` (checked directly) confirms no `openai` dependency remains — consistent with `reports/final-report.md:184-190` and `ai-work-log.md Entry 5`. Per the task framing, this is treated here as a disclosed deviation, not a defect.

## 3. Questions for the learner

If the model made 3 parallel calls in one turn and the 2nd hits `REPEATED_CALL_LIMIT`, is the 3rd call's `TOOL_CALL` trace event ever recorded, or does the loop return immediately after the 2nd? Walk through what the trace would look like for that exact case (it is not covered by any existing scenario).
2. Can you construct — even manually, not necessarily as a new automated scenario — a scripted turn where `final_text` follows a `TERMINAL_ERROR` result but the text confidently asserts a fact the tool never confirmed? Trace through `agent.py` and confirm out loud what `stop_reason` and `final_answer` would be, and how a reviewer would detect the mismatch using only the returned `AgentResult`.
3. `GetAssetArgs.asset_id` uses pattern `^[A-Z]+-[A-Z0-9]+$` (`models.py:49`), which is case-sensitive and would reject `lap-204` as `INVALID_ARGUMENTS` even though `OperationsStore.get_asset` normalizes to uppercase before lookup (`data.py:56`). Was rejecting lowercase asset IDs from the model an intentional strictness choice, or should the Pydantic model itself normalize case before the pattern check?
4. Why does `.env.example` declare `ANTHROPIC_API_KEY` when, per Entry 5 of the work log, `AnthropicBedrock` actually reads AWS Bedrock bearer-token/region environment variables rather than that key? Is `ANTHROPIC_API_KEY` vestigial from an earlier draft, or used somewhere I didn't find?
5. `max_total_tool_calls`, `EMPTY_TURN`, and `MODEL_ERROR` stop paths have no scenario or test coverage. Since PROJECT.md's explicit required-path list doesn't name them, was this an intentional scoping decision, and if so, is there a plan (even informal) to exercise them before the comprehension gate, given the mentor may pick an "unseen model turn" that lands on one of these paths?

## 4. Evidence supporting mentor review

- **Loop ownership and stopping**: `run_agent` (`src/operations_agent/agent.py:26-142`) is the sole execution owner; the model only supplies `ModelTurn` via the `ModelSession` protocol (`model.py:17-18`) and never calls tools directly. Six explicit `StopReason` values (`models.py:19-25`) all resolve through a single `stop()` helper (`agent.py:43-58`) or the `COMPLETED` return, so every run ends in exactly one terminal `AgentResult`.
- **Call-ID correlation**: `ToolCall.call_id` is preserved verbatim into `ToolResult.call_id` at every return path in `tools.py:57-107` (unknown tool, invalid args, not-found, retryable, terminal, success). `ScriptedModelSession.respond` (`model.py:27-36`) actively raises `ModelGatewayError` if returned call IDs don't match expectations, and `test_model.py:8-19` verifies this raises. `ClaudeSession.respond` keys `tool_result` blocks by `result.call_id` → `tool_use_id` (`model.py:94-99`). Scenario S09 (`fixtures/scenarios.json`) and `test_agent.py:51-56` verify parallel call IDs both survive into the trace (`{"s09-status","s09-incidents"}` confirmed present as a set).
- **Validation and error mapping**: `tools.py:67-100` maps `JSONDecodeError`/`ValidationError`→`INVALID_ARGUMENTS`, unknown name→`UNKNOWN_TOOL`, and store exceptions (`ToolNotFoundError`/`RetryableToolError`/`TerminalToolError`, defined in `data.py:12-20`) to `NOT_FOUND`/`RETRYABLE_ERROR`/`TERMINAL_ERROR` — none of these paths raise past `execute()`. Verified live: `test_tools.py:23-30` and `:32-58` assert exactly these mappings, and I independently ran `registry.execute` with a lowercase asset ID and confirmed `INVALID_ARGUMENTS` with the expected Pydantic message.
- **Limits enforced by code**: `agent.py:62-64` (iteration), `:120-121` (total calls), `:123-126` (repeated signature) — all checked before dispatch, all produce a `STOP` trace event and `None` final answer. `test_agent.py:36-49` and scenarios S07/S08 confirm `tool_call_count == 2` at the repeated-call stop and `iterations == 3` at the iteration-limit stop; I re-ran `uv run operations-agent scenario S07` / `S08` and the trace output matches the final report's claimed excerpts exactly.
